# 缓存双写一致性详解：四种时序、延迟双删、CDC 与 Outbox

> 复习优先级：P0 · 整理与来源核验：2026-09-05

**题目背景：** MySQL 是权威数据源，Redis 保存可重建的查询结果；多个服务实例可能同时读写同一个对象。讨论的是通用缓存设计，不绑定某个个人项目。先读 [一致性概览](./consistency.md)，本页负责展开并发时序和方案边界。

**选题依据与事实依据分开：** [小林 coding 的缓存一致性专题](https://xiaolincoding.com/redis/architecture/mysql_redis_consistency.html)用于对照公开面试问题覆盖；[Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)与[AWS Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)用于核对模式语义。下文时间线和数值是本站构造的反例，不是线上统计。

<a id="q-cache-01"></a>
## Q-CACHE-01：数据库和缓存怎样保持一致？

**面试开场回答：** 对可容忍短暂陈旧的读多写少数据，我采用 Cache-Aside：读时先查缓存，未命中再查数据库并回填；写时提交数据库事务后删除缓存。删除失败需要可恢复的重试，TTL 作为兜底。但它不是强一致协议：两个系统之间有失败窗口，旧读请求还可能在删除之后回填旧值。需要进一步确认可接受的陈旧时间、读副本策略，以及是否要求读己之写。

这个回答不能停在“先写库再删缓存”。面试官真正能继续检查的是：**为什么是这个顺序、它还会在哪里失败、补充机制到底修复了哪个问题。**

## 1. 四种操作顺序：必须能够自己推出反例

假设初始 `DB=0, Cache=0`。A、B 是不同请求；表中的每个步骤都已经完成后才进入下一步。

| 方案 | 一个合法交错 | 最终状态 | 问题 |
| --- | --- | --- | --- |
| 写数据库 → 更新缓存 | A 写库 1；B 写库 2；B 更新缓存 2；A 更新缓存 1 | DB=2，Cache=1 | 缓存写入顺序与数据库提交顺序相反 |
| 更新缓存 → 写数据库 | A 更新缓存 1；B 更新缓存 2；B 写库 2；A 写库 1 | DB=1，Cache=2 | 缓存提前发布尚未确定的数据；写库失败更难处理 |
| 删缓存 → 写数据库 | A 删除；B 未命中，读库 0 并回填；A 写库 1 | DB=1，Cache=0 | 删除和提交之间，读请求重新装入旧值 |
| 写数据库 → 删缓存 | 缓存原本不存在；B 读库 0 后暂停；A 写库 1 并删除；B 恢复并回填 0 | DB=1，Cache=0 | 旧读请求晚回填 |

这些交错说明“两个命令都成功”不足以证明一致。第四种方案仍适合作为常见基线，是因为数据库先决定业务结果、缓存可以按需重建，**不是因为其他交错从此不可能发生**。Microsoft 明确提示 Cache-Aside 自身不提供数据库与缓存间的一致性保证。[S1]

<KnowledgeDiagram name="cache" />

**追问：Redis 比 MySQL 快，第四种情况是不是可以忽略？** 不能用平均耗时代替时序保证。请求可以在读库后被暂停、网络延迟、GC 或线程调度都可延长回填时间。这里不需要声称某种情况“很常见”，只要构造出合法执行就能否定“绝不发生”。

## 2. 为什么删缓存，而不是直接更新缓存？

删除表达的是“这份副本已失效”，不必马上构造新值。例如一个商品详情缓存包含商品、价格和活动三种数据，修改一张表后立刻重算所有关联内容，可能引入额外查询，还可能混合不同时间点的数据。

两次删除同一个 key 的最终效果通常相同，而两次写入不同缓存值具有顺序要求。删除也体现按需加载：一个以后不会再访问的数据，没有必要在每次更新时都重建缓存。这是设计权衡，不是“更新缓存永远错误”。若业务需要 write-through、版本化物化视图等方案，应明确其写入协议和成本。[S1][S2]

**常见误答：** “数据库更新成功就先返回，异步线程里删一下即可。”进程可能在启动异步线程前崩溃；内存中的重试任务也可能随进程丢失。可靠性问题没有因代码变成异步而消失。

## 3. 删除放在事务的哪个时刻？

应区分执行了 `UPDATE` 和事务已经 `COMMIT`。构造下面的执行：

```text
A：BEGIN → UPDATE（未提交）→ DEL cache
B：缓存未命中 → 新事务读取仍可见的旧值 → 回填旧值
A：COMMIT
```

即使代码看起来是“先 UPDATE 再 DEL”，仍可能产生旧缓存。删除应安排在成功提交之后，且提交之后到删除之前的进程崩溃窗口要有恢复机制。

`afterCommit` 回调解决的是调用时点，不是持久化投递。回调尚未执行时进程退出，仍需要日志、Outbox 或 CDC 等恢复来源。本段是根据事务提交边界构造的推导；不是声称一个回调能够自动提供分布式事务。

## 4. 延迟双删为什么不能给出万能等待时间？

一种常见变体是先删除、更新数据库，然后经过延迟再删除一次；也有人采用写库后立即删除、再延迟删除。两者都试图覆盖旧读请求的回填窗口，应先说明自己讨论的是哪一种。

如果希望第二次删除覆盖所有早先读请求，延迟至少要覆盖这些请求可能经历的读取、排队、暂停和回填时间。但一般服务并不能为暂停、网络故障、重试以及副本落后提供一个绝对上限。把 `sleep(500ms)` 换成延迟消息，可以避免阻塞业务线程，却不会使这个时间假设自动成立。

**回答重点：** 延迟双删是降低特定竞态影响的工程措施，不是强一致证明。选择延迟时看实际分布，并保留过期、可恢复投递和异常监控；不能把某个博客里的等待值当通用结论。[S2]

## 5. TTL 能保证“数据库提交后 T 秒内一致”吗？

不一定。假设数据库在第 0 秒提交新值，旧请求直到第 20 秒才回填旧缓存，并从回填时开始设置 60 秒 TTL。只考虑这份缓存，它可存活到第 80 秒，而不是提交后的第 60 秒。

如果还有副本延迟、不断发生的旧回填，窗口会进一步变化。要讨论有界陈旧，必须说明读取源、新旧版本判断、最长请求寿命与过期起点。单纯“每个缓存有 TTL”只能约束某一次写入后的寿命。

**读己之写与强一致也不同。** 某个用户写成功后的一段时间读主库，可以改善该用户读己之写的体验，但不能直接推出所有用户、所有副本都满足线性一致。

<a id="q-cache-02"></a>
## Q-CACHE-02：Outbox、MQ 和 CDC 分别解决什么？

**Outbox 的核心：** 同一数据库事务同时写业务记录和待投递事件。两者一起提交或一起回滚。投递器之后读取事件并执行缓存失效或向 MQ 发送；数据库提交后进程崩溃，也不会丢掉已经持久化的发送意图。[S3]

```sql
-- 教学结构：业务表与事件表必须处在同一个数据库事务中。
CREATE TABLE cache_invalidation (
    event_id VARCHAR(64) PRIMARY KEY,
    entity_id BIGINT NOT NULL,
    entity_version BIGINT NOT NULL,
    state VARCHAR(16) NOT NULL,
    retry_at TIMESTAMP NULL
);

-- 同一个事务内：
-- UPDATE product SET price = ?, version = version + 1 WHERE id = ?;
-- INSERT INTO cache_invalidation (...) VALUES (...);
-- COMMIT;
```

这里没有把 SQL 注释包装成可以直接接生产的投递系统。实际还需事件领取、超时重领、退避、归档和告警。

| 崩溃点 | 可能后果 | 恢复原则 |
| --- | --- | --- |
| 业务提交前 | 业务和事件都回滚 | 不投递该事件 |
| 提交后、发送前 | 事件尚未送达 | 从持久化记录重试 |
| 发送后、标记完成前 | 事件被重复发送 | 接受至少一次投递，消费者处理重复 |
| 消费后、确认前 | 消费者再次收到同一事件 | 删除可重复；其他副作用需业务幂等 |

**MQ 不是 Outbox 的替代证明。** “提交 DB 后发 MQ”仍有提交成功、发送前崩溃的窗口。Outbox 解决本地数据与事件意图的原子保存；MQ 解决传输、缓冲和消费，职责不同。

**CDC 是另一种获得已提交变更的路线。** 它从数据库变更日志传播更新，减少逐条改业务写代码的需要，但引入位点保存、日志保留、初始快照、Schema 变更和消费延迟管理。Debezium 的 MySQL 连接器文档具体描述了快照与 binlog 读取过程。[S4]

**它们共同没有解决什么？** 删除消息可靠送达以后，旧读请求依然可能回填。解决“事件有没有丢”和解决“缓存能不能接受旧版本”是两个不同问题。

## 6. 带版本更新为什么也会翻车？

考虑规则 `incoming.version >= cached.version` 才接受缓存值。缓存存在 v2 时，v1 会被拒绝；但如果失效操作连 v2 版本号一起删掉，缓存重新变空，v1 又可能被当成首次填充接受。

一种候选方案是额外保留版本水位，写入时原子比较水位；但它又提出新的问题：水位何时更新、会不会过期或被淘汰、全部写入方是否都遵守、删除对象怎样表示、主从切换后水位是否回退。仅在 Redis 内用 Lua 原子比较，也不等于和 MySQL 提交形成原子操作。

**结论不是“版本号没用”，而是必须明确它所保护的状态和故障范围。** 只在缓存对象内部加一个 `version` 字段不构成完整一致性协议。

## 7. 面试中怎样做最终选型？

| 业务约束 | 可解释的起点 | 必须说明的代价 |
| --- | --- | --- |
| 展示型数据，可短暂陈旧 | Cache-Aside、过期与可恢复失效 | 回源、陈旧窗口、删除失败 |
| 写入传播不能丢 | Outbox 或 CDC + 幂等消费 | 积压、重复、顺序、运维 |
| 需要用户读己之写 | 写后返回权威值、版本约束或特定读主策略 | 路由、会话语义、额外读负载 |
| 某次判断必须基于权威状态 | 在权威存储的事务边界执行判断 | 放弃缓存收益；仍需选对隔离与并发协议 |

不要用缓存展示值决定最终扣款、唯一性或余额约束；这些不变量需要由实际写入端保护。这里是设计原则与推导，不是承诺“只要读主库就自动拥有全系统强一致”。

## 8. 带答案的追问

**重复 DEL 会不会出错？** 不会凭空把新值写成旧值，但可能删除后来生成的新缓存并降低命中率；旧请求随后回填的竞态仍在。

**把数据库写入和缓存写入都加同一把锁就够吗？** 只有所有相关路径都遵循协议、锁有效期和故障语义也被考虑，才有可能约束交错。只锁写请求，没有阻止读线程的晚回填；租约过期后的旧持有者也不能被忽略。

**读从库能有什么额外问题？** 主库已提交、缓存已删除时，从库还可能没追上，新读请求也会取到旧值。此时问题不是之前那个暂停的读请求。

**该监控什么？** 失效事件最老年龄、失败重试量、死信量、回源并发、命中率，以及抽样的数据库与缓存版本差异；“MQ 没积压”并不能证明缓存值都正确。

## 如何验证

按上述表格固定交错，分别暂停在读库后、提交后、投递后、确认前。用重复事件、乱序事件和从库落后来扩展用例。已有 [逻辑实验](../projects/experiments.md)只能证明指定竞态可复现，不代表完成真实 Redis/MySQL 故障测试。
