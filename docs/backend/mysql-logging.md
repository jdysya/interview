# MySQL 日志：redo、undo、binlog 与恢复边界

> 复习优先级：P1 · 整理与来源核验：2026-09-05

适用：MySQL 8.4 / InnoDB。目标：区分日志的职责、持久化时点和故障模型，不把“提交成功”解释成所有副本已经同步。

<a id="q-db-05"></a>
## Q-DB-05：三种日志分别解决什么问题？

**60 秒回答：** redo 支撑崩溃恢复中的重做；undo 支撑事务回滚与一致性读所需的旧版本；binlog 记录 Server 层的变更事件，用于复制和结合备份做时间点恢复。它们不能互相替代。还要说明刷盘策略、复制方式、存储可靠性与恢复目标。

| 日志 | 主要问题 | 不能据此承诺什么 |
| --- | --- | --- |
| redo | 数据页尚未落盘时，如何重做已持久化日志中的修改 | 不能代替完整备份或跨区域容灾 |
| undo | 如何撤销修改、重建历史版本 | 不能理解成永久保留的历史审计库 |
| binlog | 如何传播变更、按备份后的事件恢复 | 不能只靠 binlog 自动恢复所有丢失的数据文件 |

## 写入路径的教学拆解

一次 UPDATE 涉及执行 SQL、定位记录与加锁、生成所需 undo 和 redo、修改缓冲池页面、提交协调、返回客户端，以及后续刷脏页。不要把这些步骤简单画成“先把整页刷盘再返回”。Server binlog 与存储引擎提交之间需要协调，否则复制看到的事务与引擎恢复的事务可能不一致。

这是概念路径，不替代具体版本的实现时序。讨论两阶段提交时，应先限定为 MySQL 内部协调，不要把它与跨多个业务服务的 Saga 混为一谈。

## 面试中的故障矩阵

| 故障 | 应问什么 | 不能直接下的结论 |
| --- | --- | --- |
| mysqld 进程退出 | 哪些日志已写入 OS、哪些已同步到持久介质？ | 不等于整机掉电 |
| 主机掉电 | 刷盘策略、硬件缓存和存储保证是什么？ | OS 写成功不必然等于持久化 |
| 客户端超时 | 事务到底提交没有？能否按业务号查证？ | 超时不等于回滚 |
| 主从切换 | 复制与确认方式是什么？新主已接收并应用到哪里？ | 主库成功不等于任意副本都最新 |

## 如何验证

在专门的故障实验环境记录以下配置和版本，再设计不同故障位置；本页只给观察命令，不建议在真实业务库做断电测试。

```sql
SELECT VERSION();
SHOW VARIABLES WHERE Variable_name IN
('innodb_flush_log_at_trx_commit', 'sync_binlog', 'binlog_format');
```

建立带唯一业务请求号的测试表，记录客户端确认和恢复后行状态，分别统计“确认成功却丢失”“确认未知但存在”。这样能区分持久性问题和响应丢失问题。实验报告还应列出存储、复制和容器环境，不能只报数据库参数。
