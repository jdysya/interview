# 缓存双写、一致性与幂等

> 复习优先级：P0 · 整理与来源核验：2026-09-05

## 面试题：数据库更新后删除缓存，就能保证强一致吗？

**60 秒回答：** 这是常见 Cache-Aside 写路径，通常仍是最终一致。写库成功但删缓存失败，或者读线程读取旧数据库值后延迟回填，都可能留下旧缓存。需要说明允许的陈旧窗口，再选重试、TTL、版本、CDC 或一致性更强的读取策略。

## 典型竞态

1. 读请求缓存未命中，从数据库读取旧值 v1。
2. 写请求将数据库更新为 v2，删除缓存。
3. 先前读请求把 v1 写入缓存。

因此“先写库再删缓存”本身不能消除所有竞态。延迟双删也依赖时间假设，不能宣称严格一致。

## 可选设计

| 约束 | 可考虑方案 | 代价 |
| --- | --- | --- |
| 可接受短暂陈旧 | Cache-Aside + TTL + 删除重试 | 存在不一致窗口 |
| 需要可靠更新传播 | 事务内 Outbox 或 CDC 驱动失效 | 需处理积压、重放与顺序 |
| 防止旧版本覆盖 | 版本校验与受控缓存写入 | 所有写入方必须遵循协议 |
| 关键请求必须最新 | 读权威数据源/明确一致性协议 | 延迟和资源成本更高 |

## 面试题：幂等键怎么设计？

绑定业务动作，如 `order_id + operation + version`。相同键重复请求应返回相同业务结果；相同键但参数不同应拒绝或明确报冲突。持久化唯一约束与状态记录通常比只在 Redis 设置短 TTL 更可靠。

## 常见追问

- **消息队列能自动解决双写吗？** “提交数据库后再发消息”仍有崩溃窗口，需要可靠衔接机制。
- **幂等是否意味着函数无副作用？** 不意味着，只要求重复操作的业务效果符合约定。
- **锁成功后为什么还要查状态？** 可能是重试、重复投递或此前执行结果未知。
