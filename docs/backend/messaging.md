# Kafka、消息可靠性与消费幂等

> 复习优先级：P0 · 整理与来源核验：2026-09-05

## 面试题：Kafka 的 exactly-once 能保证数据库只写一次吗？

**60 秒回答：** 必须限定范围。Kafka 的幂等生产者和事务可以在支持的 Kafka 读写链路中提供相应语义，但不能自动把外部 MySQL 写入纳入同一原子事务。消费后更新数据库，需要业务幂等、唯一约束或事务记录来应对重投。

## 生产、存储、消费分层

- 生产端：确认策略、幂等、重试、发送超时和失败处理。
- Broker：副本、ISR、允许的最小同步副本等配置决定故障下的可用性与耐久性。
- 消费端：业务完成与 offset 提交存在时序窗口；先提交可能丢处理，后提交可能重复。
- 外部副作用：用业务键记录处理结果，必要时把去重记录与本地更新放进同一事务。

## 面试题：如何保持顺序？

Kafka 主要提供分区内顺序。相同业务实体应稳定路由到同一分区，消费侧也要避免对同一实体乱序并行。扩分区可能改变映射，需要讨论重分配期间的顺序要求。

## 常见追问

- **消息积压怎么排查？** 比较生产速率、消费处理耗时、分区倾斜、下游限流和重试；消费者数超过分区数不能让同组所有消费者都有工作。
- **毒消息怎么办？** 限制重试并隔离，保留原消息和错误信息，修复后可控重放；隔离可能影响严格顺序。
- **重复请求与重复消息一样吗？** 都需要业务幂等，但请求超时和消费 offset 产生重复的路径不同。
