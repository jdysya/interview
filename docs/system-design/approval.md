# 场景设计：审批工单与本地数据一致性

> 复习优先级：P0 · 整理与来源核验：2026-09-05

## 题目与边界

调用远端服务创建审批工单，同时把工单 ID 写入本地业务表，远端支持撤销。希望失败时不留下不一致数据。以下为方案设计，不代表已经实现或验证过某个公司的系统。

## 60 秒回答

本地事务不能覆盖远端工单。使用业务请求号保证远端创建幂等并支持状态查询；本地表保存请求号、关联 ID 和处理状态；通过状态机、重试与撤销补偿达到可恢复的最终一致。若要求任何瞬间都原子一致，需要远端参与相应事务协议，普通 HTTP/Dubbo 调用加注解无法实现。

## 不新增表时怎么做？

在现有业务表扩展或复用经过明确设计的字段，例如 `request_id、approval_id、sync_status、retry_count、next_retry_at、version`。必须先落下可恢复的处理意图，否则进程在远端成功后崩溃，后台可能无法知道应查证哪个工单。

“远端失败时不落库”需要进一步澄清：可以保证不提交**成功业务状态**，但可靠恢复通常仍需要保存处理中/失败意图。如果连现有行的状态或请求号都不允许保存，就不能承诺崩溃后的自动补偿可靠性。

## 故障矩阵

| 发生点 | 应对 |
| --- | --- |
| 远端明确拒绝 | 标记失败，不置业务成功 |
| 调用超时、结果未知 | 按 request_id 查询，不直接判定失败后重复创建 |
| 远端成功、本地关联失败 | 重试写关联；业务决定放弃时请求幂等撤销 |
| 撤销失败或超时 | 持久化补偿状态，重试/查证并告警 |
| 多次重复提交 | 请求号、唯一约束、CAS 与入口锁配合 |

## 常见追问

- **先远端再本地，catch 后撤销够吗？** 不够，进程可能在进入 catch 前崩溃。
- **撤销等于数据库 rollback 吗？** 不是，撤销是新的业务动作，有自身失败与权限条件。
- **如何表述项目成果？** 只描述实际完成的机制与验证证据；设计方案与已落地结果分开。
