# 场景设计：秒杀、库存预占与释放

> 复习优先级：P0 · 整理与来源核验：2026-09-05

## 题目与业务不变量

设计有限库存的抢购流程，先明确限购、支付时限、库存权威源和预占口径。核心不变量是不能超卖、不能重复创建业务订单，以及预占必须能够转扣减或释放。此方案是教学设计。

## 60 秒方案

入口限流削峰，按业务请求去重；库存服务原子检查可用量并预占；订单创建后进入待支付，支付完成转扣减，超时或取消释放。每步都有状态、版本与幂等键，外部步骤失败由可重试补偿处理。

## 数据约束

库存口径示例：`可售 = 实际 - 预占`。预占更新应由库存权威服务进行条件校验，例如在事务内用条件 UPDATE 保证可售足够，并检查影响行数。入口 Redis 锁不能替代库存域的原子约束。

预占记录至少能定位 `reservation_id、business_id、item_id、quantity、version、status`。同一动作重试复用幂等键；取消后再次预占是新业务轮次，使用新版本。

## 状态竞争

| 当前状态 | 请求 | 允许变化 |
| --- | --- | --- |
| 已预占 | 支付确认 | 原子转为已扣减 |
| 已预占 | 超时取消 | 原子转为已释放 |
| 已扣减 | 迟到的超时取消 | 拒绝直接释放，按售后规则处理 |
| 已释放 | 重复取消 | 返回已有结果 |

支付与超时并发时由 CAS/状态机决定唯一合法迁移，不能两个消费者分别“读状态再无条件写”。

## 追问与验证

- **预占失败是否可以降级？** 只有业务明确接受且旧逻辑仍能防超卖时才可降级，不能绕过库存保护。
- **延迟消息丢了怎么办？** 持久化到期时间并用扫描补偿；延迟消息只是触发方式之一。
- **Redis 库存和数据库不一致怎么办？** 明确谁是权威源，设计对账、冻结与修复，不能两边随意写。

故障测试覆盖预占成功回执丢失、订单失败、重复支付、取消与支付竞态。检查最终库存不变量与悬挂预占数量。
