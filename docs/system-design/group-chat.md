# 场景设计：群聊与消息同步

> 复习优先级：P0 · 整理与来源核验：2026-09-05

## 题目与需求澄清

确认群规模、在线连接数、消息速率、历史保留、撤回、离线同步和“已读”的定义。此处设计文本群聊，媒体内容通过对象存储引用传递。

## 60 秒方案

客户端保持长连接，网关负责连接与身份，消息服务负责群权限、业务去重、会话序号和持久化，投递服务推送在线用户，离线用户按游标拉取。先定义“已接收”表示持久化到何种程度，避免前端显示发送成功但服务端未保存。

## 数据与接口

消息记录包含 `conversation_id、message_id、client_message_id、sender_id、seq、payload、created_at`。客户端重发同一条消息时复用 client_message_id，服务端在发送者和会话范围内去重。seq 用于会话内顺序与补拉，不需要全平台总顺序。

## 可靠性设计

- 发送、服务端持久化、接收端收到、用户已读是四个不同状态。
- 推送可能重复或乱序，客户端按 message_id 去重，按 seq 展示并检测缺口。
- 重连时携带最后确认游标，分页同步，不能依赖一次推送永远成功。
- 消息落库与待投递事件需可靠衔接，可用 Outbox/CDC 等机制。
- 小群可采用写扩散，大群更适合按需拉取或混合方案，权衡写放大与读取成本。

## 面试追问

- **Redis 在线状态准确吗？** 断网、超时与多端登录会导致短暂偏差，不能当作唯一送达事实。
- **如何扩展网关？** 保存用户到连接位置的路由，处理迁移、心跳和连接关闭，避免业务状态只在单机内存。
- **撤回能物理删除所有副本吗？** 通常是产生状态事件并控制后续展示；已经被客户端读取的内容不能保证收回。

## 验证

测试断线重连、重复发送、跨网关投递、消息持久化后进程崩溃、超大群突发。验证无遗漏的游标同步与去重，而不是仅看到一条消息成功弹出。
