# RAG 检索面试详解：切块、Embedding、混合召回、重排与评测

> 复习优先级：P0 · 整理与来源核验：2026-09-05

**本页不是个人文档工作流。** 使用通用产品手册检索场景，解释可迁移到客服、企业搜索、知识库问答的机制。先修：[RAG 概览](./rag.md)、[检索概览](./retrieval.md)。

选题对照 [Datawhale 公开面试问题中的 RAG 部分](https://github.com/datawhalechina/hello-agents/blob/main/Extra-Chapter/Extra01-%E9%9D%A2%E8%AF%95%E9%97%AE%E9%A2%98%E6%80%BB%E7%BB%93.md)和 [JavaGuide AI 面试目录](https://javaguide.cn/ai/interview-questions/ai-interview-guide.html)。前者是作者整理的经历，不是全行业频率统计；技术结论依照文末文档和论文核对。本文的参数网格和数字例子均为教学设定，不是实测提升。

## 1. Embedding 和 Reranker 有什么本质区别？

**Embedding 检索：** 通常分别计算问题向量和文档向量，再依据指定的距离函数查找相近向量。文档向量可以预先计算并建索引，因此适合大集合召回。

**Cross-Encoder 重排：** 把问题与某一个候选片段一起输入模型，直接对这个配对计算相关性。它可以进行 query-document 之间的交互，但每个问题都要重新对候选评分，不宜把百万文档全部逐一重排。Sentence Transformers 的官方示例就是先召回候选、再进行 Cross-Encoder 排序。[S1]

| 对比 | Bi-Encoder 召回 | Cross-Encoder 重排 |
| --- | --- | --- |
| 输入组织 | 问题和文档分别编码 | 问题与候选一起编码 |
| 文档侧计算 | 可提前完成并建索引 | 不能只靠一个预计算向量完成配对打分 |
| 主要职责 | 从大集合缩小候选范围 | 在候选集合内细分相关性 |
| 无法修复的问题 | 向量相近不等于答案正确 | 候选里根本没有正确证据 |

**追问：为什么不用更大的 Embedding 模型替代重排？** 两者的交互方式不同；更大模型是否更有效需要在同一语料上比较。还要计入重建索引、存储、延迟和语言适配，不能只比较通用排行榜。

## Q-RAG-01：如何选择切块策略，又怎么证明是切块出了问题？

切块不是只为避开上下文长度限制。一个段落同时混合多个主题时，单向量表示可能无法突出用户问的局部信息；块太小又可能丢失限定条件。[S2]

用一个**合成条款**理解这一点：

```text
标题：设备保修 / 电池
正文：普通电池保修一年。
例外：因非授权维修导致的损坏不在保修范围。
```

用户问“经过非授权维修后电池损坏，是否仍有一年保修？”如果只召回第一句，回答“一年”表面上有引用，却漏掉例外。因此要标注的是回答需要的证据范围，而不是只看有没有命中“电池”两个字。

| 切块方案 | 机制 | 适合的起点 | 具体失败方式 |
| --- | --- | --- | --- |
| 固定 Token + overlap | 按长度切，重复相邻边界 | 快速建立基线 | 例外跨边界，重复块占据 Top-K |
| 标题 / 段落切分 | 按已有文档结构组织 | 手册、制度、FAQ | 标题脱离正文，超长章节不受控 |
| 父子块 | 小块检索，回读受控父段 | 条款与上下文关联强 | 父块吞掉预算，多个子块重复召回同一父块 |
| 表格专用切分 | 行与表头、单位绑定 | 参数表、统计表 | 数值失去列名、单位或有效日期 |

**一个可执行的实验设计，而非万能参数：** 在固定语料上试 `256/512/1024 Token` 与 `0/64/128 Token overlap`，确保 overlap 小于块长；结构化切块作为另一个候选。记录召回质量、最终上下文总 Token、索引体积和检索延迟。参数只是候选网格，不能说“512 一定最好”。

改变切块后 chunk ID 会变化，应把金标准绑定到原文位置或稳定段落，再映射到新块。否则沿用旧 ID，会把标注失效误判成检索退化。还应固定生成模型，先检查原文完整性、解析结果、可检索证据和召回结果，再谈 Prompt。

## 3. 为什么关键词检索和向量检索要组合？

关键词检索利用词项匹配，对错误码、产品型号、函数名等精确标识往往有帮助；向量检索可以补充表达变化和语义相近的匹配。两个召回通道的优势和失败点应通过自己的问题集合验证，不能写成“稀有词一定只能靠 BM25”。[S1]

**为什么不能直接把分数相加？** BM25 分数与向量相似度不天然处在同一尺度。即使每路单独排序有效，`0.5 * bm25 + 0.5 * cosine` 也不意味着两者贡献相等。可以经过校准后融合，也可以使用只依赖排名的 RRF。

RRF 的一种无权重形式如下，`c` 是平滑常数，rank 从 1 开始，某一路未召回的文档在该路贡献为 0：[S3]

```text
RRF(d) = 各召回列表中 1 / (c + rank(d)) 的总和
```

**手算例子，c=60：** 关键词返回 `[A, B, C]`，向量返回 `[B, D, A]`。

| 文档 | 计算 | 分数约值 |
| --- | --- | --- |
| B | 1/62 + 1/61 | 0.03252 |
| A | 1/61 + 1/63 | 0.03227 |
| D | 1/62 | 0.01613 |
| C | 1/63 | 0.01587 |

结果为 `B, A, D, C`。这里展示的是排名融合，不是“B 一定能回答问题”。RRF 不会读取文本，也不会证明文档真实性；它不是语义 Reranker。

下面是本站编写、仅依赖 Python 标准库的实现。一次列表内重复的文档先去重，避免同一个通道通过重复 ID 给文档加分；同分按 ID 排，便于测试复现。

```python
from collections import defaultdict


def rrf(rankings: list[list[str]], constant: int = 60) -> list[tuple[str, float]]:
    if type(constant) is not int or constant < 1:
        raise ValueError("constant must be a positive integer")
    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        unique_ids = list(dict.fromkeys(ranking))
        for rank, doc_id in enumerate(unique_ids, start=1):
            scores[doc_id] += 1.0 / (constant + rank)
    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))


assert [doc for doc, _ in rrf([["A", "B", "C"], ["B", "D", "A"]])] == ["B", "A", "D", "C"]
assert rrf([["A", "A", "B"]]) == rrf([["A", "B"]])
assert rrf([]) == []
```

## 4. ANN 召回变差，就一定要换 Embedding 吗？

不一定。先分开**表示质量**和**近似索引误差**：用相同向量、相同过滤条件、相同距离函数做精确扫描基线，再比较 ANN 的结果。如果精确扫描能找到证据，ANN 却找不到，优先排查索引和搜索参数；两者都找不到，再排查表示、语料与问题表达。

pgvector 文档具体列出了 HNSW、IVFFlat 与查询过滤的行为：近似索引在某些过滤路径下会返回不足数量的结果，可根据执行方式考虑 iterative scan、过滤列索引或分区。不要把一个产品的过滤实现说成所有向量数据库都一样。[S4]

**追问：加了 `tenant_id` 后结果只剩两个，是否调低相似度阈值？** 先看执行计划及候选数量，确认是合法语料不足，还是近似候选被过滤耗尽。调阈值不能修复所有召回路径问题；更不能移除权限条件来凑够 K 个结果。

## 5. 多轮改写与 Query Expansion 怎么避免改坏问题？

考虑“它的期限呢？”这类问题：检索系统需要从允许使用的对话中确定“它”指代的对象。改写目标是形成可检索的独立问题，不是替用户增加新事实。

可以同时保留原问题与改写问题两路召回；记录实体、时间、版本、否定词是否发生变化。例如“哪些情况不支持退款”被改成“退款支持条件”，可能让例外条件丢失。

多查询扩展会增加调用和候选数量，也会引入无关材料。不要只看 Recall；还要观察最终预算下证据覆盖、噪声比例和端到端延迟。本节是通用设计建议，不绑定某个框架的默认配置。

## Q-RAG-02：明明召回了正确证据，为什么回答仍然错误？

<KnowledgeDiagram name="rag" />

按阶段保留 ID，不要只保存最后的回答：

```text
原文证据 → 解析后段落 → 召回候选 → 重排结果
         → 最终上下文 → 回答中的事实与引用
```

| 失败位置 | 怎样证明 | 优先修改 |
| --- | --- | --- |
| 原文有，解析后没有 | 对照标题、表格、单位、例外条款 | 解析、清洗 |
| 可检索，候选中没有 | 查原文位置与检索日志 | 表示、关键词、过滤、召回深度 |
| 候选有，重排后丢失 | 固定候选对比排名 | 重排模型、截断规则 |
| 排名高，没进入上下文 | 检查 context_ids 与预算 | 去重、父块回读、证据分配 |
| 上下文完整，答案错误 | 人工或确定性规则检查证据支持 | 模型、指令、计算工具 |
| 答案对，引用错 | 对齐 claim 与引用段落 | 引用绑定和渲染 |

Lost in the Middle 论文观察到，所测模型对长上下文中相关信息的位置存在敏感性，尤其是信息处在中间时。这是实验现象，不应写成“所有最新模型必然如此”；但它说明输入容得下，不等于模型一定可靠使用。可设计证据位置置换实验，同时保持文本内容和长度不变。[S5]

## 7. Top-K 应该设多少？

至少区分三件事：每路召回深度、融合/重排候选数、最终放进 Prompt 的证据数。直接用一个 `top_k=5` 概括整个链路，会掩盖候选在何处被截断。

例如下面是**教学起点**，不是推荐给所有业务的最优配置：每路召回 40，融合去重后保留 50 个候选重排，最终按 3000 Token 的证据预算装入。若每块约 600 Token，不能因为“前十名都不错”就直接放十块；也不能把 5 个互相重复的块当成 5 份独立证据。

优先保留回答所需条件的覆盖，然后再比较更多候选是否带来有效收益。基准必须同时记录质量、延迟和成本，不能用更大预算换来的提升冒充算法本身更优。

## 8. 评测指标要会计算，而不只是会念名字

假设某题所需相关证据集合是 `{A, C}`，前三个返回项为 `[B, A, D]`：

```text
Recall@3 = 召回的相关证据数 / 全部相关证据数 = 1/2
Precision@3 = 前三项中的相关证据数 / 3 = 1/3
该题 RR@3 = 第一个相关项排名的倒数 = 1/2
MRR@3 = 对多道可评估问题的 RR@3 求平均
```

这些是指标定义的手算，不是真实模型评测。Hit@K 只问是否命中过至少一项，不能代替多证据问题的 Recall。对没有答案的题，Recall 分母为零，应单独统计拒答正确率、错误断言等，不能随意记成满分抬高平均值。详见 [评测实践](./evaluation-lab.md)。

**面试追问：答案正确就够了吗？** 不够。有些模型凭参数知识猜对了，但引用不支持结论；在更新频繁或需审计的任务中仍不满足目标。需要分别检查答案正确性、证据支持、引用定位、拒答与访问范围。

## 9. 一套能解释归因的调优顺序

先冻结语料版本和问题集；建立关键词或向量单路基线；再分别改变切块、融合、重排、上下文组织；最后更换生成模型。每一步保留候选和失败样本，开发集用于调参，保留集用于最终比较。

**不要把所有建议都一次打开。** 同时改 Embedding、Chunk、Prompt 和模型，最终变好也无法解释原因。文档应记录哪一步修复了哪个可复现的错误，而不是只写“综合优化提升效果”。

## 如何验证

RRF 代码可以独立运行。文档位置映射、ANN 基线、权限与证据位置实验需要实际语料和检索服务；本页没有把这些待运行实验写成已测出结果。合成评测数据只用于验证指标逻辑。
